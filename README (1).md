# 하루신문 — 나의 하루를 뉴스로

> 계정에 하루의 기록을 모으고, 하이라이트를 고르면 개성 있는 AI 기자들이 나를 주인공으로 한 신문을 발행한다.

## 문서 상태와 변경 우선순위

이 문서는 제품·UX·개발 설계 README이다. 실행 가능한 Flask 프로젝트는 아직 구현하지 않았으며 설치 명령은 구현 후 추가한다.

최신 개정은 로그인·계정 DB, 주제 카드, 기록 추가/수정/삭제, 모바일 촬영, 모듈형 지면, 날짜별 아카이브와 다중 내보내기를 반영한다. 이전 설계와 충돌하면 이 문서를 우선한다.

- 직접 작성형: 한 번에 여러 체크박스를 선택하는 방식에서 **주제 카드 → 개별 템플릿 → 저장 → 대기실**로 변경.
- 자동 포함형: 날씨·스포츠·운세·포춘쿠키는 계속 체크만 한다. 일일 본문 입력을 요구하지 않는다.
- 하이라이트: 오늘 저장한 전체 직접 기록 중 하나를 선택한다.
- 발행: ‘신문 발행하기’가 AI 생성·배치·저장을 시작한다. 성공한 발행본은 자동 아카이빙하고 수정은 새 버전으로 관리한다.

## 1. 디자인 고정 기준

- 승인된 16:9 시안의 크림색, 블루 리본, 수채화·잉크 선 일러스트 유지.
- girly·whimsical·aesthetic 분위기, 핑크 편중 없이 버터 옐로·레드 포인트 사용.
- 한글·영문 모두 Pretendard. 명조체·세리프체 미사용.
- 이모지 대신 커피잔·카메라·책·티켓·꽃 등의 일러스트 사용.
- 직접 작성형 카드와 자동 코너 그룹을 가는 구분선으로 분리.
- 저장할 때마다 ‘오늘 모은 조각’에 사진·일러스트가 누적.
- 발행 성공 시 리본이 풀리고 신문이 펼쳐지는 연출. 모션 감소 설정에서는 간단한 전환 제공.
- 16:9는 데스크톱 시안 기준. 모바일은 세로 재배치하며 스토리 출력은 별도 9:16.
- 레퍼런스: [Digibouquet](https://digibouquet.vercel.app/).

## 2. 서비스 이용 흐름

### Step 1. 로그인과 이어 쓰기

홈에는 서비스 이름·일러스트·‘오늘 신문 채우기’를 배치한다. 비로그인 사용자는 아이디·비밀번호로 로그인하거나 회원가입한다. 유효한 로그인 세션이 있으면 대기실로 바로 진입한다.

계정의 고유 username을 로그인 식별자로 사용한다. 비밀번호는 해시로 저장한다. 사용자별 DB에서 오늘 기록·자동 코너 선택·하이라이트·진행 중 작업을 복원한다. 브라우저 저장소만을 영구 보관 수단으로 사용하지 않는다.

신문 이름·기사 속 사용자 호칭·시간대는 최초 설정에서 받고 매번 다시 묻지 않는다. 날짜는 사용자 시간대 기준 YYYY-MM-DD, 서버 타임스탬프는 UTC로 저장한다.

### Step 2. 주제별 대시보드

대시보드와 발행 대기실은 한 화면에서 연결한다. 사용자는 원하는 주제 카드를 눌러 해당 개별 템플릿으로 들어간다. 처음부터 모든 주제를 고를 필요가 없다.

**직접 기록할 이야기 — 카드 버튼**

- 일상·기억하고 싶은 순간
- 오늘의 기분
- 음식·카페
- OOTD
- 음악
- 책·마음에 남은 구절
- 공연·전시·영화

---

**체크만 하면 들어가는 코너 — 포함 체크박스**

- [ ] 오늘의 날씨
- [ ] 사주·별자리 운세
- [ ] 포춘쿠키

직접 기록 카드에는 ‘기록 없음’ 또는 ‘기록 2개’와 ‘추가 기록’을 표시한다. 같은 주제의 기록을 여러 번 만들 수 있다. 자동 코너의 체크는 포함 여부만 저장하고 가짜 Entry를 만들지 않는다.

### Step 3. 주제별 템플릿과 사진

| 주제 | 핵심 입력 | 선택 입력 |
|---|---|---|
| 일상·순간 | 무슨 일이 있었는지 | 사진, 시간·장소, 감상 |
| 기분 | 기분, 이유 한 줄 | 사진, 기억할 말 |
| 음식·카페 | 음식 또는 카페 이름, 감상 | 사진, 장소, 함께한 사람 |
| OOTD | 옷·스타일 설명 | 착장 사진, 포인트 아이템 |
| 음악 | 곡명·아티스트 | 링크, 들은 상황·감상 |
| 책·구절 | 책 이름, 구절 또는 감상 | 저자, 페이지, 사진 |
| 공연·전시·영화 | 종류, 작품·행사명, 감상 | 티켓 사진, 관람일·장소 |

위 항목은 초기 템플릿 제안이다. 해당 주제의 핵심 필드만 필수로 두고, **사진 없이 텍스트만 저장**할 수 있다.

사진은 ‘사진 촬영’과 ‘갤러리에서 선택’ 버튼을 구분한다. 모바일 촬영에는 `input type="file" accept="image/*" capture="environment"`를 활용한다. capture는 기기·브라우저에 따라 동작하는 힌트이며 후면 카메라 실행을 강제하지 못한다. 필요한 접근 요청은 OS·브라우저가 처리한다. 미지원·거부·취소 시 갤러리 선택 또는 텍스트 작성을 계속할 수 있다. 갤러리에는 capture 없는 별도 입력을 사용한다. [MDN capture 문서](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture)

사진 미리보기·교체·삭제를 제공한다. 서버는 이미지 형식·용량을 검증하고 회전 보정·썸네일 생성·위치 메타데이터 제거를 수행한다. 개인 사진은 공개 static 폴더 밖에서 소유권을 검사해 제공한다.

‘저장’을 누르면 계정 DB에 기록을 저장하고 대기실로 돌아간다. 저장 실패 시 입력을 유지한다. 저장하지 않고 나갈 때는 임시 보존 또는 이탈 확인을 제공한다. 기록 저장 단계에서는 AI 기사를 생성하지 않는다.

### Step 4. 발행 대기실과 하이라이트

오늘 저장한 모든 기록을 사진 또는 일러스트·주제·원본 한 줄·시간으로 보여준다. 각 카드에 [수정] [삭제]가 있다.

- 수정: 해당 주제 템플릿에 기존 내용을 채워 연다.
- 추가: 같은 주제에도 새 기록을 생성하며 기존 기록을 덮어쓰지 않는다.
- 삭제: 확인 후 삭제하고 취소 또는 휴지통 복구를 제공하는 방향으로 설계한다.
- 포함 제외: 이번 신문에서만 제외하며 원본을 삭제하지 않는다.

오전의 음악, 점심의 음식, 저녁의 영화가 한 날짜에 계속 쌓인다. 재접속해도 유지한다. 자동 코너는 직접 작성 기록 수와 별도로 표시한다.

발행 전에 오늘 기록 전체에서 **구체적인 기록 하나**를 하이라이트로 선택한다. 주제에 기록이 여러 개라면 주제명만 선택하지 않고 어떤 기록인지 확정한다. 하이라이트는 새 글을 요구하지 않으며 1면 기사·대표 사진의 기준이 된다.

자동 코너는 개인 하이라이트 후보에서 제외한다. 하이라이트를 삭제하거나 포함에서 제외하면 새 선택이 필요하다. 직접 기록이 하나도 없다면 선택 상태는 보존하되, 개인 신문 발행에는 기록 하나를 먼저 요청한다.

### Step 5. AI 기자단과 신문 발행

하이라이트·포함 기록·자동 코너를 확인한 뒤 ‘신문 발행하기’를 누른다. 서버는 원본 스냅샷을 고정하고 AI 생성 → 구조 검증 → 지면 배치 → 발행본 저장을 수행한다. 중복 클릭은 같은 작업으로 처리한다.

기자 페르소나 제안:

| 기자 | 담당 | 원칙 |
|---|---|---|
| 특종 기자 | 1면 하이라이트 | 눈에 띄는 제목과 핵심 사건, 원본 사실 유지 |
| 찌라시 기자 | 1면의 짧은 가십 코너 | 사용자 기록에 근거한 장난스러운 관찰, 허위 소문·발언 금지 |
| 일상 기자 | 일상·기분 | 다정한 관찰, 감정 임의 추정 금지 |
| 미식 기자 | 음식·카페 | 사용자가 쓴 맛과 경험을 소개 |
| 스타일 기자 | OOTD | 실제 입력한 착장과 포인트 설명 |
| 문화 평론가 | 음악·책·공연·영화 | 이용자의 감상과 기자의 해석을 구분 |
| 브리핑 기자 | 날씨·스포츠 | 출처와 갱신 시각이 있는 데이터 활용 |
| 포춘 에디터 | 운세·포춘쿠키 | 재미로 보는 코너로 구분 |
| 편집장 | 전체 내용 | 중복 제거·우선순위·허용 분량 조정 |

개인 기사에서는 이용자를 제3자로 서술한다. 예: ‘새 카페에서 커피를 마시며 쉬었다’ → ‘지수는 새로 찾은 카페에서 커피를 마시며 잠시 쉬어가는 시간을 보냈다.’

페르소나는 문체를 바꾸고 사실을 유지한다. 원본에 없는 타인의 반응·인용·장소·사건을 생성하지 않는다. 경기 결과를 선택했다고 사용자가 직접 관람한 것처럼 쓰지 않는다. 찌라시도 근거 없는 스캔들 대신 일상의 유쾌한 해석으로 한정한다.

여러 기자는 역할 구분이며 같은 모델에 다른 지시문을 적용할 수 있다. AI는 구조화된 기사 데이터만 반환하고 임의 HTML/CSS를 생성하지 않는다.

생성 중 조각이 모이고 리본으로 묶이는 연출을 보여준다. 실패하면 원본과 이전 발행본을 유지하고 재시도한다. 기록이 변경되어 오래된 결과가 되면 현재 초안 위에 자동 적용하지 않고 재생성 또는 스냅샷 확인을 안내한다.

### Step 6. 펼침·내보내기·날짜별 아카이브

성공한 발행본을 계정과 날짜에 저장한 뒤 ‘짠’ 하고 리본이 풀리고 신문이 펼쳐진다. 애니메이션을 끝까지 보지 않아도 저장은 완료되어 있어야 한다. 기본 공개 범위는 나만 보기다.

결과와 과거 아카이브에서 다음 행동을 제공한다.

| 기능 | 결과 |
|---|---|
| 이미지 저장 | 스토리용 1080×1920 PNG. 표지 요약 또는 페이지별 여러 장 |
| PDF 저장 | 전체 신문을 페이지 단위로 인쇄·보관 |
| 공유하기 | 지원 기기에서 생성한 이미지 파일을 시스템 공유창으로 전달 |
| 기사 수정 | 현재 발행본을 유지한 채 수정 초안 생성, 재발행 시 새 버전 |

인스타그램 스토리로의 무조건적인 직접 이동·자동 게시를 약속하지 않는다. Web Share API는 기기별 공유창을 열며 대상 앱은 환경에 따라 다르다. HTTPS에서 파일을 준비한 뒤 `navigator.canShare({files})`로 확인하고 사용자의 버튼 클릭에 따라 공유한다. Instagram이 공유 대상으로 나타나면 사용자가 선택한다. 취소는 발행 실패로 처리하지 않는다. 공유 지원이 없거나 원하는 앱이 없으면 PNG 저장 후 Instagram에서 직접 올리는 경로를 제공한다. 이미지 클립보드 복사는 추가 지원 기능으로만 검토하며 필수 경로로 삼지 않는다. [MDN Web Share 문서](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share)

아카이브에는 달력·날짜별 표지·월별 탐색을 제공한다. YYYY-MM-DD별 신문에서 원본 기록, 최신 발행본, 이전 발행 버전을 구분한다. 다시 다운로드할 때 AI를 재호출해 다른 기사를 만들지 않고 저장된 발행본으로 재출력한다.

## 3. 유동적 지면 — 고정 틀과 동적 모듈

### 역할 분리

- 디자이너/개발자: 그리드, 모듈 종류, 사진 비율, 여백, 페이지 분할, 글자 크기 규칙 정의.
- AI 기자/편집장: 제목·요약·본문·우선순위와 허용된 모듈 타입 추천.
- 레이아웃 엔진: 기록 수·사진 유무·실제 텍스트 높이에 맞춰 검증된 모듈을 배치.

AI의 모듈 추천도 허용 목록을 검사한다. 직접 HTML/CSS를 만들게 하지 않는다.

### 1면

항상 사용자가 선택한 하이라이트와 짧은 찌라시 코너를 중심으로 구성한다. 제호·날짜·호수는 고정 위치다. 대표 사진이 없으면 큰 제목과 텍스트 중심 레이아웃을 사용한다. 기록이 적을 때 찌라시는 짧게 쓰고 빈 공간을 허위 내용으로 채우지 않는다.

### 2면 이후

나머지 기록과 체크한 자동 코너를 모듈형 그리드로 배치한다. 텍스트형·사진형·인용형·LP형·티켓형·짧은 브리핑형 모듈을 준비한다. 주제와 기록이 많으면 필요한 만큼 후속 페이지를 추가하고, 후속 내용이 없으면 2면을 만들지 않는다.

기본은 읽기 순서가 명확한 CSS Grid/Flex 구성이다. Masonry와 같은 시각적 흐름이 필요해도 DOM의 논리적 읽기 순서를 유지한다. 출력물은 웹의 무한 스크롤 화면을 그대로 캡처하지 않고 고정 크기 페이지 템플릿으로 재배치한다.

넘침 처리는 허용 범위 안의 요약 → 큰 모듈 선택 → 다음 페이지로 분할 순서로 한다. 원본 기록은 보존하며, 읽기 어렵게 글자를 계속 줄이거나 본문을 잘라 숨기지 않는다. 중요한 사실은 짧은 요약으로 생략될 수 있으므로 기사 수정 화면에서 원본도 확인할 수 있게 한다.

## 4. 자동 코너

| 코너 | 오늘 사용자 행동 | 데이터·설정 |
|---|---|---|
| 날씨 | 포함 체크 | 최초 설정 지역의 실제 날씨 |
| 스포츠 | 포함 체크 | 최초 설정 응원 팀의 실제 경기 결과 |
| 사주·별자리 운세 | 포함 체크 | 미리 설정한 운세 방식·필요 프로필 |
| 포춘쿠키 | 포함 체크 | 개인정보 없이 오락용 문구 제공 가능 |

설정이 없으면 미설정, 공급자가 없으면 미연동, 경기 일정이 없으면 경기 없음으로 표시한다. 임의 데이터를 실제 정보처럼 제공하지 않는다. 위치 권한을 묵시적으로 가정하지 않는다. 사주 계산은 별자리·일반 AI 운세와 구분하며 실제 계산 모듈 없이 개인 사주 분석으로 표시하지 않는다.

## 5. 데이터 구조

| 모델 | 주요 책임 |
|---|---|
| User / UserSettings | 고유 username·비밀번호 해시·신문 이름·호칭·시간대·지역·팀 |
| TopicDefinition | manual/automatic, 입력 스키마·버전, 일러스트, 기본 persona_id |
| DailySelection | 사용자·날짜별 자동 코너 포함 상태 |
| Entry / Media | 날짜·주제·필드·사진·수정 버전·소유자·삭제 상태 |
| EditionDraft | 포함 entry_ids, 자동 코너, highlight_entry_id, 수정 초안 |
| ReporterPersona | 기사 역할·문체·사실 보존 규칙 |
| GenerationJob | 입력 스냅샷·진행·기사 후보·오류·중복 방지 키 |
| EditionRevision | 발행 날짜·호수·버전·기사·지면·미디어·외부 데이터 스냅샷 |
| ExportJob | revision_id별 PDF/PNG 출력·완료 파일 |
| ShareLink | 선택한 발행본의 읽기 전용 링크·만료·해제 |

계정·날짜별 신문은 하나의 논리적 묶음이고 재발행은 새 revision이다. 원본 수정·삭제가 기존 발행본을 자동 수정하지 않도록 한다. 발행본이 참조하는 사진은 원본 기록 삭제 후에도 유지한다. 신문 자체를 삭제하면 해당 공유 링크도 해제한다. 다운로드된 외부 복사본까지 회수되지는 않는다.

## 6. Flask 구현 방향과 API 변경

Flask/Jinja·관계형 DB·비공개 파일 저장·백그라운드 생성/출력 작업을 유지한다. 계정 접근은 세션 기반이며 변경 요청에 CSRF 검증, 개인 리소스마다 소유권 검사를 수행한다. 서버에서만 AI 키를 사용한다.

| 목적 | 제안 API |
|---|---|
| 가입·로그인·로그아웃 | POST /api/v1/auth/signup, /login, /logout — username/password |
| 주제 카드·템플릿 | GET /api/v1/topics |
| 오늘 대기실 | GET /api/v1/days/:date |
| 자동 코너 포함 | PATCH /api/v1/days/:date/selections |
| 사진 업로드 | POST /api/v1/media |
| 기록 저장·수정·삭제 | POST /api/v1/entries, PATCH/DELETE /api/v1/entries/:id |
| 날짜별 기록 | GET /api/v1/entries?date=YYYY-MM-DD |
| 신문 초안 구성 | POST /api/v1/editions, PATCH /api/v1/editions/:id |
| 발행 요청 | POST /api/v1/editions/:id/publications — 202, job_id 반환 |
| 발행 작업 조회 | GET /api/v1/publications/:job_id — 완료 시 revision_id 반환 |
| 아카이브 | GET /api/v1/editions?from=&to=&cursor= |
| 특정 발행본 | GET /api/v1/editions/:id/revisions/:revision_id |
| 수정 기사 후보 생성·적용 | POST /api/v1/editions/:id/generations, /apply-generation |
| 출력 생성·상태·다운로드 | POST /api/v1/editions/:id/exports, GET /api/v1/exports/:id, /exports/:id/download |
| 공유 링크 생성·해제 | POST /api/v1/editions/:id/shares, DELETE /api/v1/shares/:id |

publications는 이번 개정의 발행 전체 작업 진입점이다. 내부 생성과 최종 snapshot 저장을 관리하고, 이전 설계의 별도 publish API는 내부 서비스로 통합해 중복 발행 경로를 피한다. 수정 초안이 있으면 사용자 수정본을 유지하고 불필요하게 AI로 전부 재작성하지 않는다.

PATCH와 발행 요청에는 현재 version을 포함하고 오래된 요청은 충돌로 응답한다. 발행·출력은 Idempotency-Key로 중복 처리한다. 작업 상태는 queued/running/succeeded/failed. 필수 기사 생성 실패는 자동 발행하지 않는다. 외부 자동 코너 장애는 사용자에게 알려 재시도 또는 해당 코너 제외 후 발행을 선택하게 한다.

## 7. 검증 기준과 구현 순서

1. 승인된 디자인의 로그인·주제 카드·자동 체크 코너·대기실을 구현한다.
2. 주제별 입력·사진 선택/촬영·저장·수정·삭제를 연결하고 재로그인 유지와 타인 접근 차단을 확인한다.
3. 오늘 전체 기록에서 하이라이트를 선택하고, 원본 변경·삭제 시 선택 유효성을 검사한다.
4. 기자 페르소나·사실 기반 기사·고정 1면·유동적 후속 지면을 구현한다.
5. 발행 작업 중복·실패·재시도와 자동 아카이빙, 이전 발행본 보존을 확인한다.
6. 기록 1개/여러 개, 사진 없음/세로 사진, 긴 제목/긴 본문에서 모바일·PDF 잘림을 검증한다.
7. PNG·PDF·지원 환경의 시스템 공유, 미지원 환경의 다운로드 대체 경로를 확인한다.
8. 날짜별 과거 발행본 재열기·수정본 재발행·재다운로드를 확인한다.

운영 전 확정할 항목: AI 모델·비용 한도, 외부 데이터 공급자, 계정 복구 방식, 업로드 용량·형식, 삭제 복구 기간, 운영 저장소·백업 정책. 이는 핵심 기록과 아카이브의 제품 흐름을 변경하지 않는다.
